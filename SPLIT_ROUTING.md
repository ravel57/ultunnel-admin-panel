# control.ultunnel.ru — раздельная маршрутизация

Отдельный эндпоинт того же приложения `ultunnel-admin-panel`. Делает две вещи:

1. принимает от клиентского приложения имена доменов, которые посетил пользователь;
2. даёт пользователю решить по каждому домену — идти ему через VPN, мимо VPN или
   быть заблокированным, — и отдаёт это решение обратно приложению.

Авторизация одна: **secret key, который генерирует админка**. Тот же ключ, что и
для скачивания конфигурации; админ может выдать новый кнопкой рядом с ключом в
карточке пользователя (`POST /api/v1/regenerate-secret-key/{userId}`).

## Как это собрано

| Слой | Где | Что делает |
|---|---|---|
| nginx | [`nginx/control.ultunnel.ru.conf`](nginx/control.ultunnel.ru.conf) | Отдельный vhost. Проксирует в то же приложение, но наружу пускает только `/control` — админский API и форма логина с этого хоста возвращают 404. |
| API | `ru.ravel.ultunneladminpanel.controller.control.ControlApiController` | `/control/api/v1/**`, авторизация по ключу. |
| Логика | `service/control/SplitRoutingService.kt` | Приём доменов, правила, выдача конфигурации, ночная чистка истории. |
| Данные | `model/control/` | `visited_domain`, `split_routing_rule`, `user_control_settings`, `control_rules_state`. Таблицы создаются автоматически (`ddl-auto: update`). |
| Фронт | `ultunnel-front`, `src/components/control/` | Перенесённые из `mikrotik_parser` элементы: `SegmentedControl`, `AppAlert`, карточки со списком доменов. Одна страница: поиск и список своих доменов с переключателем режима. |

Один и тот же бандл фронта обслуживает оба сайта: `App.vue` смотрит на имя хоста
(`control.*`) или путь `/control` и показывает либо админку, либо панель
раздельной маршрутизации.

## Общий список правил

Маршрутизация, которую отдаёт API, по умолчанию собрана из включённых правил
**всех** подписчиков: они складываются в общий пул, и новый пользователь сразу
получает список, который до него уже кто-то разметил.

Опция **«Только мои домены»** живёт в клиентском приложении и передаётся
параметром `onlyMine=true` — тогда в ответе только правила этого пользователя.
Параметр принимают все методы, на сервере он не хранится, поэтому клиент шлёт
его в каждом запросе.

Разрешение конфликтов:

* **своё правило всегда главнее пула** — если подошло хоть одно собственное,
  пул по этому домену не смотрят вовсе;
* внутри пула для одного шаблона берётся режим, который выбрало больше всего
  людей; при равенстве — тот, что меняли последним. Большинством, а не «кто
  последний, тот и прав», именно чтобы один подписчик не мог в любой момент
  перекинуть домен для всех;
* в `/routing/singbox` свои правила идут раньше пуловых — sing-box берёт первое
  подошедшее, так что порядок и реализует это правило.

**История посещений общей не становится.** `GET /visits` при любых параметрах
возвращает домены только того пользователя, чей ключ предъявлен: один подписчик
не должен узнать, какие сайты открывает другой. Общими становятся лишь правила,
которые люди осознанно включили.

`rulesVersion` это учитывает: при работе с пулом в него входят и чужие правки,
поэтому опрашивать версию надо с тем же `onlyMine`, с каким потом забираются
правила.

## Авторизация

Ключ передаётся заголовком:

```
X-Secret-Key: <secretKey>
```

Принимается также `Authorization: Bearer <secretKey>` и — для совсем простых
клиентов, которые умеют только собрать URL — параметр `?secretKey=`. Веб-интерфейс
им не пользуется: ключ в query попадает в логи прокси и в историю браузера.

Ответы: `401` — ключ не найден, `403` — подписка выключена (`isEnabled = false`).

Веб-интерфейс можно открыть сразу авторизованным: `https://control.ultunnel.ru/?key=<secretKey>`.
Ключ будет считан, сохранён в `localStorage` и убран из адресной строки.

## API

Базовый адрес: `https://control.ultunnel.ru/control/api/v1`

Все методы принимают необязательный `onlyMine` (по умолчанию `false` — общий пул).

Машиночитаемое описание — [openapi/control-api.yaml](openapi/control-api.yaml)
(OpenAPI 3.0.3, только этот контроллер): годится для генерации клиента, в том
числе `swift-openapi-generator`.

### Что нужно клиентскому приложению

#### `POST /visits` — отправить посещённые домены

```json
{
  "deviceId": "laptop",
  "entries": [
    {"domain": "ya.ru", "address": "5.255.255.242", "hits": 3},
    {"domain": "github.com"}
  ]
}
```

Короткая форма — только имена:

```json
{"domains": ["ya.ru", "github.com"]}
```

`address`, `hits`, `at` необязательны. Имена нормализуются: схема, порт, путь и
завершающая точка отбрасываются, регистр приводится к нижнему, IDN переводится в
punycode. Голые IP-адреса отбрасываются — эндпоинт собирает имена. За один запрос
не больше `app.control.max-domains-per-report` имён (по умолчанию 2000).

Ответ:

```json
{"accepted": 2, "rejected": 0, "stored": true, "rulesVersion": 7}
```

`stored: false` означает, что пользователь выключил сбор — отчёт принят и отброшен.

#### `GET /routing/version` — дешёвый опрос

```json
{"rulesVersion": 7, "rulesUpdatedAt": "2026-11-14T09:12:03Z", "defaultMode": "PROXY", "onlyMyDomains": false}
```

Полный список правил имеет смысл забирать, только когда `rulesVersion` вырос.

#### `GET /routing/singbox` — готовый фрагмент маршрутизации

```json
{
  "rulesVersion": 7,
  "final": "proxy",
  "rules": [
    {"domain": ["login.example.com"], "outbound": "direct"},
    {"domain_suffix": ["gosuslugi.ru", "nalog.ru"], "outbound": "direct"},
    {"domain_keyword": ["doubleclick"], "outbound": "block"}
  ]
}
```

Правила подставляются в секцию `route` **перед** собственным правилом приложения
«всё из tun в туннель», `final` задаёт режим по умолчанию. Теги `proxy`, `direct`
и `block` — те же, что уже есть в конфигурациях, которые отдаёт
`/api/v1/get-users-proxy-servers-singbox`.

Порядок групп — точные хосты, затем суффиксы, затем вхождения: sing-box берёт
первое подходящее правило, поэтому более точное должно идти раньше.

#### `GET /routing/plain` — то же самое текстом

```
# ultunnel split routing
# version: 7
# default: PROXY
DIRECT DOMAIN login.example.com
DIRECT SUFFIX gosuslugi.ru
BLOCK KEYWORD doubleclick
```

### Что нужно веб-интерфейсу

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/me` | Имя пользователя, настройки и статистика одним запросом. Им же проверяется ключ при входе. |
| `GET` | `/stats` | Только статистика. |
| `GET` | `/visits?find=&mode=&ruled=&limit=&offset=` | **Свои** собранные домены с их действующим режимом и `ruleSource` (`OWN` / `SHARED` / `DEFAULT`). `mode` — `PROXY`/`DIRECT`/`BLOCK`, `ruled` — только со своим правилом или только без. |
| `DELETE` | `/visits` | `{"domains": [...]}` или `{"all": true}` — убрать из истории. Правила не трогает. |
| `GET` | `/rules` | **Собственные** правила пользователя и режим по умолчанию; пул сюда не попадает — он виден в `/routing/*`. |
| `POST` | `/rules` | Создать или изменить. `{"patterns": [...], "mode": "DIRECT", "matchType": "SUFFIX"}`. **`mode: null` удаляет правила** — домены возвращаются под режим по умолчанию. |
| `DELETE` | `/rules` | `{"ids": [...]}` или `{"patterns": [...]}`. |
| `GET` | `/settings` | Режим по умолчанию, сбор доменов, версия правил. |
| `POST` | `/settings` | `{"defaultMode": "PROXY", "collectEnabled": true}`. Опции «только мои домены» здесь нет: она принадлежит клиенту и ездит параметром `onlyMine`. |

## Режимы и совпадения

Режим (`RoutingMode`):

* `PROXY` — через туннель;
* `DIRECT` — мимо туннеля, это и есть «раздельная» часть;
* `BLOCK` — отбросить.

Тип совпадения (`DomainMatchType`), названия повторяют sing-box:

* `DOMAIN` — точный хост;
* `SUFFIX` — хост и всё под ним (`example.com` ловит и `a.example.com`);
* `KEYWORD` — вхождение подстроки.

Если домену подходит несколько правил, побеждает самое точное: точный хост важнее
суффикса, длинный суффикс важнее короткого, вхождение — последнее. Домен, под
который не подошло ни одно правило, идёт по `defaultMode`.

## Настройки приложения

`application.yaml`:

```yaml
app:
  control:
    max-domains-per-report: 2000   # сколько имён принимается за один POST /visits
    max-domains-per-user: 20000    # потолок истории; сверх него вытесняются самые старые
    max-rules-per-user: 5000
    retention-days: 30             # ночная чистка истории; 0 — не чистить
    cleanup-cron: "0 30 4 * * *"
```

Правила чистка не трогает — только собранную историю.

## Что осталось за рамками

Правила **не** вшиваются в конфигурацию, которую отдаёт
`/api/v1/get-users-proxy-servers-singbox`: она собирается шаблоном `ConfigTemplate`
отдельно под каждую платформу. Клиентское приложение забирает маршрутизацию
отдельным запросом и подмешивает её в свою секцию `route` — так правила можно
менять, не переcкачивая конфигурацию целиком.
